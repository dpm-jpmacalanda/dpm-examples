Scope & Inventory

This runbook connects Argo CD to Dynatrace in two ways. SDLC events: every Argo CD sync of a subscribed app is sent to Dynatrace, so deployments show up on the ArgoCD Application Lifecycle dashboard. Argo CD metrics: the Dynatrace ActiveGate scrapes Argo CD's Prometheus-format metrics, which fill the ArgoCD Platform Observability dashboard and the health tiles of the Lifecycle dashboard.

Owner: the Dynatrace admin — once per tenant (Step 7 once per Argo CD cluster)

Steps 1–6 deploy the OpenPipeline ingest source and pipeline for Argo CD events and two dashboards: ArgoCD Application Lifecycle and ArgoCD Platform Observability. They add new objects only. Steps 7–8 prepare metric collection.

5a What the pipeline does

The ArgoCD Application pipeline (pipeline_argocd_application_v2) runs three processors, in this order:

ProcessorAdds
1. Add ArgoCD deployment propertiesStatus, outcome, duration, Git revision, deployment name and namespace, health, sync status, project. argocd.app.name from label app or name; argocd.app.stage from stage or environment
2. Enrich Argo CD eventImages and image tag; version = image tag; owner (label owner, else project); branch and repository on started events; sync initiator; deployment count and previous revision; app URL; chart path, source type, Helm release and values files; parent app; sync policy; applied resources; health-since and created times
3. Clean upRemoves the raw payload (app). Must stay last: any processor that reads app has to run before it
5b Updating an existing deployment

Deploy over the existing objects; do not undeploy first. monaco delete would remove the ingest source (syncs in between are lost) and recreate the dashboards with new IDs (links break). Monaco has no state file: it matches objects by project name, config type and config ID, and the pipeline by its fixed ID, so the same manifest updates them in place from any repository.

  • Processors edited by hand in the UI are replaced by the repository version
  • Both dashboards are overwritten: export any edits first
  • Afterwards: one Lifecycle and one Platform Observability dashboard, three processors in the pipeline
  • Rollback: deploy the upstream community-examples folder the same way
6 Confirm and clean up

Both dashboards and the ArgoCD ingest source exist; the pipeline shows the three processors in order. Delete the platform token. Empty dashboards (“no value for variable(s)”) are normal until data arrives.

7 Turn on Prometheus exporter monitoring METRICS

Open Kubernetes, select the Argo CD cluster, then … → Connection settings → Monitoring settings. Turn on Monitor annotated Prometheus exporters and save. Repeat per Argo CD cluster.

8 Histogram ingest — decide METRICS OPTIONAL

Settings → Metrics → Histograms → Ingest complete explicit bucket histograms. Needed only for duration percentiles (for example Reconciliations Performance).

Tenant-wide and cost-relevant. The setting has no cluster or namespace scope: every Prometheus or OpenTelemetry histogram sent to the tenant keeps its buckets, which multiplies data points. Turn it on only after the Dynatrace admin agrees, and compare usage before and after.
Success Indicators: deploy without errors → 2 dashboards and ArgoCD ingest source → three processors in order → platform token deleted → exporter monitoring on (metrics) → histogram decision recorded

Phase 4: Configure Argo CD — Events and Metrics

Owner: the platform team — per Argo CD cluster. One Helm values change, one upgrade run.

All changes go into the Argo CD Helm values, so they survive upgrades and reinstalls and can be reviewed. Merge each block into the existing section of the values file; a second top-level notifications: or controller: block creates duplicate keys and Helm keeps only one.

1 Add the notifications config (SDLC events)
notifications:
  enabled: true
  metrics:                           # METRICS (optional)
    enabled: true                    # Notifications Delivery tile
  podAnnotations:                    # METRICS: pod OR service annotations
    metrics.dynatrace.com/scrape: "true"
    metrics.dynatrace.com/port: "9001"   # container port
  secret:
    items:
      dt-base-url: "https://<tenant-id>.live.dynatrace.com"
      dt-access-token: "set-at-deploy-time"      # placeholder, never the real token
  notifiers:
    service.webhook.dynatrace-webhook: |
      url: $dt-base-url
      headers:
        - name: Authorization
          value: "Api-Token $dt-access-token"
        - name: Content-Type
          value: "application/json; charset=utf-8"
  templates:
    template.dynatrace-webhook-template: |
      webhook:
        dynatrace-webhook:
          method: POST
          path: /platform/ingest/custom/events.sdlc/argocd
          body: |
            {
              "app": {{toJson .app}}
            }
  triggers:
    trigger.dynatrace-webhook-trigger: |
      - when: app.status.operationState.phase in ['Succeeded'] and app.status.health.status in ['Healthy', 'Degraded']
        send: [dynatrace-webhook-template]
      - when: app.status.operationState.phase in ['Failed', 'Error']
        send: [dynatrace-webhook-template]
      - when: app.status.operationState.phase in ['Running']
        send: [dynatrace-webhook-template]
Indentation of the template matters. Everything under template.dynatrace-webhook-template: | must be indented 2 spaces deeper than the key. If webhook: starts in the same column, YAML ends the text block: the template becomes empty and a stray webhook key breaks the ConfigMap.

$dt-base-url and $dt-access-token stay literal; Argo CD fills them from the Secret. The chart passes {{toJson .app}} through unchanged.

2 Add the metrics annotations METRICS
controller:
  metrics:
    enabled: true

      annotations:
        metrics.dynatrace.com/scrape: "true"
        metrics.dynatrace.com/port: "8082"
server:
  metrics:
    enabled: true
    service:
      annotations:
        metrics.dynatrace.com/scrape: "true"
        metrics.dynatrace.com/port: "8083"
repoServer:
  metrics:
    enabled: true
    service:
      annotations:
        metrics.dynatrace.com/scrape: "true"
        metrics.dynatrace.com/port: "8084"
applicationSet:
  metrics:
    enabled: true
    service:
      annotations:
        metrics.dynatrace.com/scrape: "true"
        metrics.dynatrace.com/port: "8080"
# notifications controller: see Step 1 (inside the notifications block)

Keep existing prometheus.io/* annotations and ServiceMonitors; both collectors can read the same endpoints. Only the notifications controller restarts (briefly) when its metrics are switched on. Ports are cluster-internal; nothing is exposed outside the cluster.

Pod or service annotations. Dynatrace scrapes pods; an annotated Service only points it to the pods behind it. Either method works: <component>.podAnnotations (restarts that component once) or <component>.metrics.service.annotations (no restart). Use one method per component, never both, or the component may be scraped twice. metrics.dynatrace.com/port is always the container port.
One key, one place. Each key may appear only once in the values file. A second notifications:, metrics: or podAnnotations: under the same parent does not merge: the last one wins silently. Edit the existing keys (for example podAnnotations: {}) instead of adding new ones. To keep Dynatrace settings separate, use a second file with an extra -f; Helm merges files correctly.
3 Apply — token passed at deploy time
DT_SDLC_TOKEN=$(<read from your secret store>)
[ -n "$DT_SDLC_TOKEN" ] || { echo "token empty"; exit 1; }

helm upgrade <release> argo/argo-cd -n ${ARGOCD_NS} --version <chart-version> \
  -f <values>.yaml \
  --set-string notifications.secret.items.dt-access-token="${DT_SDLC_TOKEN}" \
  --dry-run          # review, then run again without --dry-run
Pass the token on every run. With notifications.secret.create: true, a run without --set-string writes the placeholder into the Secret and every event fails with 401, silently. Alternative: notifications.secret.create: false and create argocd-notifications-secret separately (for example External Secrets Operator), so Helm never manages the token.

Use the plain token: the chart writes secret.items under stringData.

Argo CD managing itself (GitOps). If the Argo CD Helm values live in Git and Argo CD syncs itself, never put the token in Git: use secret.create: false with an External Secret or sealed secret.

# secret keys present
kubectl -n ${ARGOCD_NS} get secret argocd-notifications-secret -o jsonpath='{.data}' | grep -o 'dt-[a-z-]*'
# what Helm actually deployed (compare with the values file in the repository)
helm -n ${ARGOCD_NS} get values <release> | grep -E 'dt-base-url|dynatrace-webhook|metrics.dynatrace.com'
# METRICS: notifications controller pod restarted (AGE in minutes) and annotated
kubectl -n ${ARGOCD_NS} get pods | grep notifications-controller

  | grep -i metrics
5 Subscribe the pilot apps

Add the annotation to each pilot Application manifest where it is maintained and let the normal pipeline apply it:

metadata:
  annotations:
    notifications.argoproj.io/subscribe.dynatrace-webhook-trigger.dynatrace-webhook: ""

Only for an Application not managed from Git: kubectl -n ${ARGOCD_NS} annotate application <app> notifications.argoproj.io/subscribe.dynatrace-webhook-trigger.dynatrace-webhook=""

Subscribing sends one event right away for the app's last sync. It confirms the path; it is not a new deployment. Metrics need no subscription: they cover all apps.
Alternative — kubectl (lab or quick test). The same content can be applied without Helm: kubectl patch secret argocd-notifications-secret (plain token under stringData), kubectl patch cm argocd-notifications-cm --patch-file with the service, template and trigger keys, and kubectl annotate svc for metrics. Validated in the lab, but not recorded in Helm values: it is lost if Argo CD is reinstalled and may be overwritten by the next Helm run.
Other Dynatrace samples. The azure_devops_observability sample uses the older OpenPipeline config type that replaces the whole SDLC events configuration, including the ArgoCD source. Adapt it before deploying it next to this setup, and test on a lab tenant.

5 Test a failed sync (optional, agreed with the platform team)

Set an invalid value in a pilot app's manifest (for example a non-numeric replicas) → task.outcome = failed. A Git path that does not exist → task.outcome = error. Restore and sync again.

Phase 6: 48-Hour Observation & Rollback

Owner: the platform team. Support: the Dynatrace admin watches the dashboards, reviews metric usage and revokes the token after a rollback.

During the 48 Hours

  • Every sync of a pilot app produces started and finished events, with no gaps
  • No Failed to notify or 401 in the notifications controller log
  • Argo CD, syncs and pipeline runs behave as before
  • METRICS Platform Observability stays filled; custom-metric usage is within the agreed budget
Events during a token problem are lost. Argo CD retries once, then marks the event as sent. Fix token problems quickly and expect a gap.

Production Approval

  1. Document findings and resolved issues
  2. Per-app annotations or a selector-based subscription
  3. Metrics: keep, filter or drop; histogram decision
  4. Event fields: owner label and approval to store the sync initiator
  5. Stakeholder approval for Production clusters

Rollback

No restarts of apps; Argo CD deploys normally without the integration; past data stays in Dynatrace.

1 Remove the subscriptions

Remove the annotation from the pilot Application manifests and let the pipeline apply it.

2 Remove the Dynatrace keys from the Helm values and run the upgrade

Remove the Dynatrace service, template, trigger and the two dt-* secret items, and the metrics podAnnotations if used; for metrics, set metrics.dynatrace.com/scrape: "false" or remove the annotations. Other notification settings stay.

3 Dynatrace side (the Dynatrace admin)

Delete the access token. Turn off Monitor annotated Prometheus exporters for the cluster if metrics are dropped. Dashboards and OpenPipeline objects can stay; to return to the original Dynatrace pipeline, deploy the upstream community-examples folder with Monaco.

Never delete or replace the whole argocd-notifications-cm or argocd-notifications-secret. They may hold other teams' notification settings.

Key Decisions & Rationale

  • Two data paths: SDLC events (webhook, no agent) for deployment history; Argo CD metrics (ActiveGate scrape) for platform health. Events work without metrics.
  • Helm values as the single delivery: notifications and metrics are one change in the Argo CD Helm values, so they survive upgrades and are reviewed like any other change.
  • Add, never replace: existing notification settings and Prometheus annotations are kept.
  • Pilot apps first: per-app subscription limits deployment history to the pilot apps; metrics cover all apps by design.
  • Tokens and secrets: all tokens are generated by the Dynatrace admin; the access token is passed at deploy time from the customer-approved secret store, never committed or shared externally, including with DPM.
  • Enriched events: a second OpenPipeline processor, placed before Clean up, adds the image, version = image tag, owner (label, else Argo CD project), sync initiator, deployment history and source details. The pipeline is maintained in the DPM fork of the Dynatrace sample (Apache 2.0) and deployed with Monaco over the existing objects.
  • Personal data: argocd.sync.initiated_by stores the Argo CD user name (often an e-mail); keep it only with the customer's approval.
  • Cost control: Argo CD metrics are custom metrics; histogram ingest is tenant-wide and a Dynatrace admin decision.
  • DPM support: DPM International Inc. is available throughout the timeline.
  • Maturity: the Dynatrace Argo CD tutorial is labelled Preview; the SDLC ingest API it uses is not.
